# RhythmLab · 网页端音游模拟器

4K / 7K / 无轨 谱面生成训练器，纯前端、无依赖、无构建。支持电脑键盘与手机触屏。

## 运行

直接用浏览器打开 `index.html`，或在目录下起一个静态服务器：

```bash
python3 -m http.server 8080
```

线上：<https://music.pekka.ren>（改完代码执行 `./deploy.sh` 同步）。

## 操作

| 模式 | 触屏 | 键盘 |
|---|---|---|
| 4K | 点按 4 条轨道 | `D F J K` |
| 7K | 点按 7 条轨道 | `S D F 空格 J K L`（中间那轨是拇指，紫色） |
| 无轨 | 点按键出现的位置 | 没有键位可映射，打不了 |

`Esc` 暂停。

## 无轨

没有轨道，也没有下落：**固定大小的按键直接出现在屏幕上的任意位置**，外面套一圈收缩的
提示环，环贴上按键的那一刻就是判定时刻。按键位置本身就是要瞄的东西，所以键盘天然打不了，
这个模式只在触屏设备上可选（非触屏设备上那个按钮是灰的）。

- **按键大小**默认是场地宽的 **1/6**，可调 1/4～1/10。
- **横向**沿用列模型 —— 交互 / 切 / 叠的左右手结构全在里面，丢掉就没得练了 ——
  但列心间距是按键直径的 **1.5 倍**，中间那半个按键的空就是横向抖动的余地。
  列数由按键大小反推：`floor(freeSize / 1.5)`，1/6 的按键 → 4 列（占宽 4/6，剩 1/3 全是自由量）。
- **纵向**完全自由：每只手从上一个落点开始随机游走，步长受速度预算约束 ——
  横向那一跳已经吃掉一部分 `VMAX`，剩下的才归纵向用，所以快速纵叠时手根本来不及上下动，
  而交替手（每只手的间隔是行距的两倍）能跑满整个高度。
- **不重叠是靠构造保证的，不做事后分离**：同一行里每个音符的横向抖动上限取「列间距减一个直径」
  的一半，两个音符各自朝对方抖到底也只是刚好贴住；同一只手在同一行里的音符共用一个纵向位置，
  看起来就是一串横排的和弦。`validate` 会复核同时出现的按键有没有叠上、有没有出界。
- 坐标是归一化的（`nx` 以场地宽为 1，`ny` 以场地高为 1），按固定长宽比 **0.5** 生成。
  渲染时场地**按这个比例装进屏幕并居中**，宽或高哪边先到头就以哪边为准 ——
  直接拉伸到屏幕比例会把纵向距离压扁，原本刚好贴住的两个按键就叠上了。
- 判定：点到哪个按键就打哪个，同一位置上叠着多个不同时刻的按键时，先按「离判定时刻多近」
  排，再按「离落点多近」排。命中半径 = 按键半径 + 「轨道判定余量」那个像素值。
- 原生壳的触摸直采原本只转发 x，无轨要 y，所以协议从 `类型,id,x,排队毫秒` 扩成
  `类型,id,x,y,排队毫秒`（`RhythmLabShell/4` 起）。页面两种长度都认；旧壳在无轨下
  不接管触摸，让 DOM 那一路照常跑。

## 判定

| 判定 | 默认窗口 | 得分 |
|---|---|---|
| PERFECT | ≤ 40 ms | 100% |
| GREAT | ≤ 80 ms | 50% |
| MISS | 超出 GREAT 或未击打 | 0% |

两个窗口都可以在设置页调（PERFECT 10–100ms，GREAT 20–200ms），GREAT 会自动保证不小于 PERFECT。
结果页会记下本局用的窗口，误差图也按实际窗口缩放。

**下落速度**按倍数设定，1.0 倍 = 500ms 落到判定线，范围 0.5～4.0 倍（1000ms 到 125ms）。

满分 1,000,000。输入判定使用事件自带的 `timeStamp`，不受帧率影响；音频用 Web Audio 合成节拍器与打击音。

## 节奏结构

- 主段固定 **16 分音**，没有难度滑条，难度只由 BPM 决定。
- **休息段比例**可调（默认 0，即全程 16 分音）：按比例换算成「每 N 小节休息 1 小节」，休息小节只有 **8 分音单键**。
- 乐句 = 2 小节，每个乐句重抽一次参数。

## 预设

| 预设 | 名称 | 生成规则 |
|---|---|---|
| trill_basic | 普通交互 | 两手位置每 2 小节重抽，起手强制一左一右跨中线 |
| trill_shift4 / trill_shift3 | 位移交互 | 每 4 / 3 个键两手一起平移，越界反向 |
| trill_axis | 轴交互 | 一手为轴，另一手三角波往返；可选左 / 右 / 交替为轴，三角 / X 形 / 8 形 |
| trill_converge | 交互收拢 | 两手间距随乐句缩到 0，末尾变纵连 |
| stream_single / stream_stairs | 单键切 / 楼梯 | 相邻行不共列；楼梯预设奖励同向移动 |
| js_light / js_dense | 小切 LJS / DJS | 每拍 1 / 2 个双押 |
| js_sea | 双押海 | 每一行都是双押；相邻行最多共 1 列，共列是唯一的换组出路，所以罚得重 |
| hs_light / hs_dense | 三切 LHS / DHS | 每拍 1 / 2 个多押（双押 + 三押） |
| jack_small / jack_mid / jack_big | 小叠 / 中叠 / 大叠 | 相邻行至少共 1 列；押数权重见 `generator.js` |
| jack_anchor | 纵叠 | 每行包含本乐句锚定列 |
| rand_low / rand_mid | 乱 | 随机列的单键流，基本每行一个键；「密度」指多押的多少而非留白多少，低密度约 95% 单键，中密度掺约 25% 双押 |
| mixed | 散打 | 以乱为底，按「花样比例」（默认 35%）插入其他预设的乐句；整体约 84% 的行是单键，空行约 3.5% |

交互类在 4K 和 7K 下都可用：双手连续位置模型算出坐标后映射到最近的轨道，并保证相邻音符不同列。

**位移幅度**（交互 / 纵连）拉到 0 就是**全程零位移**：各处的位移量线性收到 0，
而且乐句参数会冻结——第一个乐句抽到什么，整首一直是它，否则「每 2 小节重抽两手位置」
本身就是一次大位移。各预设下它的含义：普通交互 = 两手最多拉开多远，位移交互 = 每组平移多远，
轴交互 = 反手摆幅，收拢 = 起始间距（0 时退化成原地纵连），纵连 = 换轨最多跳几条（0 时永不换轨）。

## 生成算法

1. 种子由「种子 + 预设 + BPM + 键数 + 小节数 + 休息比例 + 交互参数」哈希得到，参数相同谱面永远相同。
2. 逐行枚举 K 列的全部组合（4K 15 种、7K 127 种）：硬约束过滤（切不共列 / 叠共列 / 锚定列 / 单列连打上限）→ 软约束打分（ABA/ABAB、楼梯、整行重复、共列数、左右手负载、单手押数）→ 按 exp(−罚分) 加权抽样 → 降押 / 放宽 / 空行兜底。
3. 交互类用双手物理模型：速度上限 3.5 屏宽/秒、两手间距 ≥ 1.02 列宽不交叉（收拢与跨手样式除外），再映射到最近列。
4. 休息段前后只放开两手的移动速度限制，列约束保持连续，避免边界处冒出假纵连。
5. `validate` 检查列越界、同刻重复列、押数超键数、同列间隔 < 45ms。

## 挑战模式

BPM 从起点逐段爬到目标，用来找自己的上限。

- **起始 BPM / 目标 BPM**：支持递增也支持递减。
- **每几小节提速一次**（默认 4）与**每次 +N**（默认 5）。
- 小节数由爬升区间自动推出（档数 × 每档小节数），上限 256 小节；超出时会截断并在提示里说明实际爬到多少。
- 变速靠逐小节累加的速度表实现：每小节有自己的 BPM，`measureTime` / `beatTimes` 给出绝对时间，音符、拍线、节拍器全部按它走。
- 游戏中 HUD 显示当前 BPM 与目标，每次提速在屏幕中间闪一次 `♪ 165 BPM`。
- 结算按 BPM 分档统计准确率，给出「95% 线守到多少 BPM」「90% 线守到多少」和最差的一档。

### 录音组

「节奏激昂」与「舒缓」共九条取自 incompetech.com（Kevin MacLeod，CC BY 4.0），都是合成器 / 鼓组驱动的电子与摇滚，
实测速度与作者标称完全一致、零漂移，循环相似度 0.72～0.95。
弱拍音乐（如纯氛围铺底）会让基于脉冲均值的速度检测往低速跑，这类曲子改用作者标注的 BPM 只做相位对齐；
拍点强度实在太低、速度标注没有意义的（如某条纯 pad，强度仅 0.13）直接淘汰。
「录音」组取自 Wikimedia Commons 的公有领域 / CC 授权录音，署名与逐条处理说明见 `audio/CREDITS.md`，
界面上也会展示并可点击跳转。挑选时只保留**速度稳定**的版本：先估计整曲速度，再比较前后半段的
速度差，真人 rubato 演奏（拍点强度 0.14、漂移 4.4%）一律淘汰，留下的都是零漂移的精确整数速度。
每条按原速截取整数小节的循环段，响度统一归一到 -13 LUFS。

播放按小节切片调度：每小节起一个音源，速率等于该小节 BPM 除以原速，相邻片段用 8ms 淡入淡出
重叠拼接。每小节重新对齐所以永不漂移；挑战模式提速时录音跟着一起加速（音高随之升高）；
每小节时长由解码后的真实时长反推，规避编码器补零造成的误差。

### 自己上传

设置页背景音下面的「＋ 上传音乐」：浏览器内解码 → 谱通量起音包络 + 自相关测一次速 →
弹出确认面板，节拍器叠在音乐上试听，对不齐就手动调 BPM 与起拍点（起拍点可调一整小节，
因为测速只定得出「拍」的相位、定不出哪一拍是重拍；试听的咔哒声每 4 拍加重，听得出来）。
确认后连同原始文件一起存进 IndexedDB，永久保留，可删除。单曲上限 30MB。

**安卓 App 里必须有 `WebChromeClient.onShowFileChooser`**：WebView 默认根本不处理
`<input type="file">`，点了连事件都不产生——表现就是「点上传按钮啥反应都没有」。
壳里实现了它（`ACTION_GET_CONTENT`，取消时也必须回调 `null`，否则那个 input 会永久卡住）。
页面按 UA 里的 `RhythmLabShell/N` 判断壳版本，旧壳直接把原因和出路写在提示里。
网页端这边文件 input 也不能用 `display:none`——部分手机浏览器会拒绝对隐藏 input 的 `.click()`。

### 合成组

由 Web Audio 现场合成，不含外部素材，好处是任何速度都能跟且不占体积。带 progression 的条目用
公有领域乐曲的和弦走向，音高轨字符指「当前和弦的第几个音」。

### 速度对齐

**BPM 永远由你决定，程序不会改动它。** 音乐靠调播放倍速来跟：内部先选一个离「谱面 BPM / 原速」
最近的 2 的幂次作为折算比例，再算出实际倍速，因此倍速始终落在 0.71～1.41 之间（音高偏移不超过
半个八度），任何 BPM 都严格同步。例如原速 160 的曲子：

| 谱面 BPM | 100 | 137 | 155 | 160 | 200 | 240 | 320 |
|---|---|---|---|---|---|---|---|
| 播放倍速 | 1.25 | 0.86 | 0.97 | 1.00 | 1.25 | 0.75 | 1.00 |

提示行会实时显示当前倍速，旁边有个「对齐到整倍速」按钮，**只在你主动点击时**才会把 BPM
挪到最近的整倍数。下拉下方也列出该曲所有整倍速的 BPM。

音频末端有压缩器加软削波两级保护，多押打击音叠背景音也不会削顶。

## 安卓 App（`android/`）

站点首页右上角可以直接下载 `RhythmLab.apk`（2.3 MB，已签名，侧载安装）。
它是一个 WebView 壳，把整个站点打进 assets 里离线运行，只做网页端做不到的几件事：

1. **`setSystemGestureExclusionRects`** —— 把屏幕左右边缘从系统手势里划出来，
   安卓 10+ 的返回手势不再从最外侧轨道抢触摸。这是网页端无论如何都做不到的，
   网页端只能靠留白躲开。壳还会把系统声明的手势区宽度喂给页面（`window.__shell`），
   轨道留白按真值走而不是靠猜。
2. **原生 MotionEvent 直采** —— 在 Activity 的 `dispatchTouchEvent` 里拿到每一个
   `ACTION_DOWN` / `ACTION_POINTER_DOWN`，用 `SystemClock.uptimeMillis() - getEventTime()`
   算出事件排队了多久，转发给 JS 还原真实按下时刻，完全绕开 WebView 的 DOM 事件管线。
   转发是攒批的：原先每个动作同步调一次 `evaluateJavascript`，高频时每秒几百次跨进程调用会
   把 `dispatchTouchEvent` 的返回拖慢，而返回慢就是 `finishInputEvent` 慢，InputDispatcher
   跟不上就发 `ACTION_CANCEL` 并停止派发——正是「只有高频才断」的样子。
3. **`onShowFileChooser`** —— WebView 默认根本不处理 `<input type="file">`，点了连事件都不
   产生。上传自己的音乐全靠它。
4. **强制横屏 + 常亮 + 沉浸式全屏** —— 没有地址栏伸缩，没有下拉刷新。

原生事件**不消费**，DOM 事件照常存在。JS 端收到原生事件就切到原生模式并忽略 DOM，
但只要 300ms 内没有原生事件而 DOM 事件来了，立刻退回 DOM 模式，不至于整个玩不了。

页面资源通过 `shouldInterceptRequest` 以 `https://rhythmlab.local/` 的假域名从 assets 喂给 WebView，
这样 origin 是正常的 https，`fetch` 加载音频不会被 `file://` 的同源策略挡住。

重新打包：`cd android && ./build.sh`（不依赖 gradle，用 aapt + javac + dx + apksigner，
需要 `/usr/lib/android-sdk` 与 JDK）。

## 横屏

手机一律横屏打：

- **安卓 App** 在 `AndroidManifest.xml` 里写死 `sensorLandscape`，整个 App（含设置页）
  只有横屏，两个方向都认。
- **网页端**在开始训练时调 `screen.orientation.lock('landscape')`。这个 API 在安卓 Chrome
  上**只有全屏时才允许调用**，所以它挂在 `requestFullscreen()` 的 resolve 上；iOS Safari
  完全不支持。
- 锁不上就用**竖屏挡板**兜底：触屏设备在游戏页里一旦是竖屏就挡一层「请把手机横过来」，
  同时把这一局暂停，免得音符白白掉过去算成 miss。转过来挡板自动收掉。
- PWA 的 `manifest.webmanifest` 也声明 `"orientation": "landscape"`，装到桌面后同样只横屏。

## PWA

站点带 `manifest.webmanifest` 与 `sw.js`，可以「添加到主屏幕」。装好后以 fullscreen 模式启动，
同样没有浏览器的下拉刷新与地址栏伸缩，核心文件与听过的音频会缓存下来离线可玩。

## 移动端触摸

手机上最常见的「断触」是手指没完全抬起就滑到别的轨，或落点压在轨道边线上。
另外有一类是**触摸在页面之外就被吃掉了**——查下来是设备厂商的手势监听器在抢，
把应用加进系统的「游戏模式」白名单即可恢复，不是页面能修的。引擎这边做的：

- 监听整个游戏层而非 canvas，`touchstart` / `touchmove` / `touchend` / `touchcancel` 全处理，
  多指按 `identifier` 分别跟踪。
- 手指滑过轨道边界即判一次击打（需滑够半个轨宽，避免边界抖动连发）。
- **轨道左右留白**（默认 48px）：安卓手势导航会吃掉屏幕最边上约 20~30px 的触摸，
  7K 时一轨才 55px，最外侧那轨有小半截压在手势带里。留白把轨道整体让开，
  留白区内点击仍算最外侧轨，只是不摆音符。原生壳里会按系统声明的手势区宽度自动抬高。
- **轨道判定余量**（默认 12px）：落点越过轨道边线这么多像素内仍算这一轨，
  而且只在本轨确实没音符可打时才生效。设 0 即严格只认按到的那一轨。
- **开始时自动全屏**，挡掉浏览器自身的下拉刷新与地址栏伸缩。
- 触摸派生的鼠标事件在 700ms 内被忽略，避免同一下吃掉两个音符。
- canvas 位置每 500ms 重新量一次，地址栏收放或旋转后不会按到错位的轨。
- 游戏中给 `body` 加 `.playing` 锁住页面，避免视口变化让判定线跳动。

### 事件时间戳换算

不同浏览器 / WebView 的 `event.timeStamp` 基准各不相同，还可能在运行中漂移。
引擎不去猜基准，而是持续记录 `performance.now() - timeStamp` 的**最小值**作为两个时钟的
真实偏移（最小值对应排队耗时≈0 的那次事件），用 `timeStamp + 偏移` 换算。这样基准是什么
都无所谓，漂移也能自动跟上，同时保留事件之间的相对精度（主线程卡顿时尤其重要）。
换算结果若突然离当下超过 1 秒，说明基准跳变，会重新锚定。

### 别让主线程卡住

安卓在应用主线程卡住期间会**直接丢掉排队的触摸**，所以「画面顿一下」和「一段完全点不上」
是同一件事。逐条解决的：

- **每次击打不再新建音频节点**，这是「越打越卡」的根因。原先每响一次打击音就新建一个
  `GainNode` 挂到总线上，而它永远不会断开——音频图随击打次数无限增长，每个渲染周期都要
  遍历，最后把线程拖死。这解释了为什么交互几乎不卡、四指狂按必卡且越来越卡。现在打击音走
  一条常驻的 `sfxBus`，BGM 每个乐器一条常驻增益节点。实测 2000 次击打新建 GainNode 从
  2000 降到 0。
- **排期音频走一条可整体切断的总线**，不再用数组持有几百个 `AudioBufferSourceNode` 等着
  一次性释放——那正好制造周期性 GC 卡顿。
- **视口变化不再重建画布**。地址栏伸缩、状态栏进出、旋转都会连发十几次 `resize`，每次中间
  尺寸都重建一块 5~11MB 的后备缓冲，足以把主线程堵上几百毫秒。现在播放中等尺寸稳定 220ms
  后才处理，且只有变化超过 10% 才真正重建，小幅变化直接改变换矩阵拉伸复用。实测连发 21 次
  resize 的重建次数从 21 降到 0。
- **渲染分辨率上限**（触屏默认 1.5 倍，桌面 2 倍）。瓶颈在光栅化不在 JS：实测归因是
  「我的代码 12ms / 代码之外 125ms」，且关掉全部声音照样卡。3 倍密度下画布是 11.3MB，
  1.5 倍只有 2.9MB。连续卡顿 3 次会自动再降一档，逐级降到 1.0，每档至少间隔 2 秒。
- **绘制减负**：轨道按下高亮原本每帧每轨一块 240px 高的渐变填充（逐像素运算），改成预渲染
  一张 1×64 的小图每帧一次 `drawImage`；音符从圆角路径改为 `fillRect`；判定线渐变缓存复用。
- **触摸事件全部被动监听**。`touchmove` 在四指按住时每秒可达近千次，非被动监听会让浏览器
  每次都同步等 JS 返回并禁用事件合并。页面已有 `touch-action: none`，不需要再 `preventDefault`。
- **输入路径零分配**：`_lanePos` 复用同一个对象返回。
- **解码后的 BGM 只留当前一条**。一条 12~16 秒立体声解码出来就是 4~5MB，五条都听过会留下
  24MB，在手机上足以造成内存压力。
- **低延迟画布**（`desynchronized`）默认开，少一层合成、快几毫秒；个别安卓设备上它会让画面
  周期性停更，设置里可关（改动后重载页面）。
- 音频末端有压缩器加软削波两级保护；打击音限流为 20ms 内最多 4 个。
- **不在打的时候自动退出全屏**：打完、暂停、返回设置都会退出，方便看结果和改设置。
- **判定偏移校准**：默认不动。结果页会报出本局的平均偏差，要用再点一下套用。

## 文件

- `js/rng.js` 可复现随机数
- `js/generator.js` 谱面生成器（可在 Node 中 `require`）
- `js/audio.js` Web Audio 合成与录音播放
- `js/bgm.js` BGM 节奏型与和弦进行定义
- `js/game.js` Canvas 渲染与判定引擎
- `js/ui.js` 设置面板、预览、结果页
- `serve.py` 带 no-cache 头的静态服务（systemd `pekka-music.service` 用它）
- `deploy.sh` 同步到线上目录

## 自检

纯 Node 的三个直接跑；带 `.py` 的走 Playwright 打真实页面，需要先起静态服务：

```bash
node tools/test_gen.js        # 全预设 × BPM × 键数 × 种子：可复现性、硬约束、押海、无轨坐标
node tools/test_shift.js      # 位移幅度 0 = 零位移；幅度 1 用满键区
node tools/test_tempo.js      # 上传测速：合成节拍信号的 BPM 与相位

python3 -m http.server 8931 --bind 127.0.0.1 &
python3 tools/test_lane.py    # 4K / 7K 端到端：逐个打准必须全中
python3 tools/test_free.py    # 无轨端到端：点准全中、点偏一个直径全空
python3 tools/test_upload.py  # 上传端到端：测速 → 保存 → 刷新仍在 → 删除
```
