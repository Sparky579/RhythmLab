# RhythmLab · 网页端音游模拟器

4K / 7K 谱面生成训练器，纯前端、无依赖、无构建。支持电脑键盘与手机触屏。

## 运行

直接用浏览器打开 `index.html`，或在目录下起一个静态服务器：

```bash
python3 -m http.server 8080
```

线上：<https://music.pekka.ren>（改完代码执行 `./deploy.sh` 同步）。

## 操作

| 模式 | 触屏 | 键盘 |
|---|---|---|
| 4K | 点按 4 条轨道 | `D F J K` |
| 7K | 点按 7 条轨道 | `S D F 空格 J K L`（中间那轨是拇指，紫色） |

`Esc` 暂停。

## 判定

| 判定 | 默认窗口 | 得分 |
|---|---|---|
| PERFECT | ≤ 40 ms | 100% |
| GREAT | ≤ 80 ms | 50% |
| MISS | 超出 GREAT 或未击打 | 0% |

两个窗口都可以在设置页调（PERFECT 10–100ms，GREAT 20–200ms），GREAT 会自动保证不小于 PERFECT。
结果页会记下本局用的窗口，误差图也按实际窗口缩放。

**下落速度**按倍数设定，1.0 倍 = 500ms 落到判定线，范围 0.5～4.0 倍（1000ms 到 125ms）。

满分 1,000,000。输入判定使用事件自带的 `timeStamp`，不受帧率影响；音频用 Web Audio 合成节拍器与打击音。

## 节奏结构

- 主段固定 **16 分音**，没有难度滑条，难度只由 BPM 决定。
- **休息段比例**可调（默认 0，即全程 16 分音）：按比例换算成「每 N 小节休息 1 小节」，休息小节只有 **8 分音单键**。
- 乐句 = 2 小节，每个乐句重抽一次参数。

## 预设

| 预设 | 名称 | 生成规则 |
|---|---|---|
| trill_basic | 普通交互 | 两手位置每 2 小节重抽，起手强制一左一右跨中线 |
| trill_shift4 / trill_shift3 | 位移交互 | 每 4 / 3 个键两手一起平移，越界反向 |
| trill_axis | 轴交互 | 一手为轴，另一手三角波往返；可选左 / 右 / 交替为轴，三角 / X 形 / 8 形 |
| trill_converge | 交互收拢 | 两手间距随乐句缩到 0，末尾变纵连 |
| stream_single / stream_stairs | 单键切 / 楼梯 | 相邻行不共列；楼梯预设奖励同向移动 |
| js_light / js_dense | 小切 LJS / DJS | 每拍 1 / 2 个双押 |
| js_sea | 双押海 | 每一行都是双押；相邻行最多共 1 列，共列是唯一的换组出路，所以罚得重 |
| hs_light / hs_dense | 三切 LHS / DHS | 每拍 1 / 2 个多押（双押 + 三押） |
| jack_small / jack_mid / jack_big | 小叠 / 中叠 / 大叠 | 相邻行至少共 1 列；押数权重见 `generator.js` |
| jack_anchor | 纵叠 | 每行包含本乐句锚定列 |
| rand_low / rand_mid | 乱 | 随机列的单键流，基本每行一个键；「密度」指多押的多少而非留白多少，低密度约 95% 单键，中密度掺约 25% 双押 |
| mixed | 散打 | 以乱为底，按「花样比例」（默认 35%）插入其他预设的乐句；整体约 84% 的行是单键，空行约 3.5% |

交互类在 4K 和 7K 下都可用：双手连续位置模型算出坐标后映射到最近的轨道，并保证相邻音符不同列。

**位移幅度**（交互 / 纵连）拉到 0 就是**全程零位移**：各处的位移量线性收到 0，
而且乐句参数会冻结——第一个乐句抽到什么，整首一直是它，否则「每 2 小节重抽两手位置」
本身就是一次大位移。各预设下它的含义：普通交互 = 两手最多拉开多远，位移交互 = 每组平移多远，
轴交互 = 反手摆幅，收拢 = 起始间距（0 时退化成原地纵连），纵连 = 换轨最多跳几条（0 时永不换轨）。

## 生成算法

1. 种子由「种子 + 预设 + BPM + 键数 + 小节数 + 休息比例 + 交互参数」哈希得到，参数相同谱面永远相同。
2. 逐行枚举 K 列的全部组合（4K 15 种、7K 127 种）：硬约束过滤（切不共列 / 叠共列 / 锚定列 / 单列连打上限）→ 软约束打分（ABA/ABAB、楼梯、整行重复、共列数、左右手负载、单手押数）→ 按 exp(−罚分) 加权抽样 → 降押 / 放宽 / 空行兜底。
3. 交互类用双手物理模型：速度上限 3.5 屏宽/秒、两手间距 ≥ 1.02 列宽不交叉（收拢与跨手样式除外），再映射到最近列。
4. 休息段前后只放开两手的移动速度限制，列约束保持连续，避免边界处冒出假纵连。
5. `validate` 检查列越界、同刻重复列、押数超键数、同列间隔 < 45ms。

## 挑战模式

BPM 从起点逐段爬到目标，用来找自己的上限。

- **起始 BPM / 目标 BPM**：支持递增也支持递减。
- **每几小节提速一次**（默认 4）与**每次 +N**（默认 5）。
- 小节数由爬升区间自动推出（档数 × 每档小节数），上限 256 小节；超出时会截断并在提示里说明实际爬到多少。
- 变速靠逐小节累加的速度表实现：每小节有自己的 BPM，`measureTime` / `beatTimes` 给出绝对时间，音符、拍线、节拍器全部按它走。
- 游戏中 HUD 显示当前 BPM 与目标，每次提速在屏幕中间闪一次 `♪ 165 BPM`。
- 结算按 BPM 分档统计准确率，给出「95% 线守到多少 BPM」「90% 线守到多少」和最差的一档。

| 节奏激昂 | Kick Shock 138 / Club Diver 140 / Blown Away 170 / Summon the Rawk 209 |

### 录音组

「节奏激昂」与「舒缓」共九条取自 incompetech.com（Kevin MacLeod，CC BY 4.0），都是合成器 / 鼓组驱动的电子与摇滚，
实测速度与作者标称完全一致、零漂移，循环相似度 0.72～0.95。
弱拍音乐（如纯氛围铺底）会让基于脉冲均值的速度检测往低速跑，这类曲子改用作者标注的 BPM 只做相位对齐；
拍点强度实在太低、速度标注没有意义的（如某条纯 pad，强度仅 0.13）直接淘汰。
「录音」组取自 Wikimedia Commons 的公有领域 / CC 授权录音，署名与逐条处理说明见 `audio/CREDITS.md`，
界面上也会展示并可点击跳转。挑选时只保留**速度稳定**的版本：先估计整曲速度，再比较前后半段的
速度差，真人 rubato 演奏（拍点强度 0.14、漂移 4.4%）一律淘汰，留下的都是零漂移的精确整数速度。
每条按原速截取整数小节的循环段，响度统一归一到 -13 LUFS。

播放按小节切片调度：每小节起一个音源，速率等于该小节 BPM 除以原速，相邻片段用 8ms 淡入淡出
重叠拼接。每小节重新对齐所以永不漂移；挑战模式提速时录音跟着一起加速（音高随之升高）；
每小节时长由解码后的真实时长反推，规避编码器补零造成的误差。

### 合成组

由 Web Audio 现场合成，不含外部素材，好处是任何速度都能跟且不占体积。带 progression 的条目用
公有领域乐曲的和弦走向，音高轨字符指「当前和弦的第几个音」。

### 速度对齐

**BPM 永远由你决定，程序不会改动它。** 音乐靠调播放倍速来跟：内部先选一个离「谱面 BPM / 原速」
最近的 2 的幂次作为折算比例，再算出实际倍速，因此倍速始终落在 0.71～1.41 之间（音高偏移不超过
半个八度），任何 BPM 都严格同步。例如原速 160 的曲子：

| 谱面 BPM | 100 | 137 | 155 | 160 | 200 | 240 | 320 |
|---|---|---|---|---|---|---|---|
| 播放倍速 | 1.25 | 0.86 | 0.97 | 1.00 | 1.25 | 0.75 | 1.00 |

提示行会实时显示当前倍速，旁边有个「对齐到整倍速」按钮，**只在你主动点击时**才会把 BPM
挪到最近的整倍数。下拉下方也列出该曲所有整倍速的 BPM。

音频末端有压缩器加软削波两级保护，多押打击音叠背景音也不会削顶。

## 安卓 App（`android/`）

站点首页右上角可以直接下载 `RhythmLab.apk`（2.3 MB，已签名，侧载安装）。
它是一个 WebView 壳，把整个站点打进 assets 里离线运行，只做网页端做不到的三件事：

1. **`setSystemGestureExclusionRects`** —— 把屏幕左右各 48dp 从系统手势里划出来，
   安卓 10+ 的返回手势不再从最外侧轨道抢触摸。这是网页端无论如何都做不到的，
   网页端只能靠留白躲开。
2. **原生 MotionEvent 直采** —— 在 Activity 的 `dispatchTouchEvent` 里拿到每一个
   `ACTION_DOWN` / `ACTION_POINTER_DOWN`，用 `SystemClock.uptimeMillis() - getEventTime()`
   算出事件排队了多久，转发给 JS 还原真实按下时刻，完全绕开 WebView 的 DOM 事件管线。
3. **常亮 + 沉浸式全屏** —— 没有地址栏伸缩，没有下拉刷新。

原生事件**不消费**，DOM 事件照常存在。JS 端收到原生事件就切到原生模式并忽略 DOM，
但只要 300ms 内没有原生事件而 DOM 事件来了，立刻退回 DOM 模式，不至于整个玩不了。

页面资源通过 `shouldInterceptRequest` 以 `https://rhythmlab.local/` 的假域名从 assets 喂给 WebView，
这样 origin 是正常的 https，`fetch` 加载音频不会被 `file://` 的同源策略挡住。

重新打包：`cd android && ./build.sh`（不依赖 gradle，用 aapt + javac + dx + apksigner，
需要 `/usr/lib/android-sdk` 与 JDK）。

## PWA

站点带 `manifest.webmanifest` 与 `sw.js`，可以「添加到主屏幕」。装好后以 fullscreen 模式启动，
同样没有浏览器的下拉刷新与地址栏伸缩，核心文件与听过的音频会缓存下来离线可玩。

## 移动端触摸

手机上最常见的「断触」是手指没完全抬起就滑到别的轨，或落点压在轨道边线上。引擎做了这些处理：

- 监听整个游戏层而非 canvas，`touchstart` / `touchmove` / `touchend` / `touchcancel` 全部处理，多指按 `identifier` 分别跟踪。
- 手指滑过轨道边界即判一次击打（需滑够半个轨宽，避免边界抖动连发）。
- **轨道左右留白**（默认 28px）：安卓手势导航会吃掉屏幕最边上约 20~30px 的触摸，7K 时一轨才 55px，
  最外侧那轨有小半截压在手势带里。留白把轨道整体让开，留白区内点击仍算最外侧轨，只是不摆音符。
- **轨道判定余量**（默认 12px）：落点越过轨道边线这么多像素内仍算这一轨，而且只在本轨确实没有
  音符可打时才生效。设 0 即严格只认按到的那一轨。7K 上固定点一条轨的蹭中率约 19%（接近 1/7 的
  理论值），不会出现「乱点都能中」。
- **开始时自动全屏**：借「开始训练」这次用户手势进入全屏，挡掉浏览器自身的下拉刷新与地址栏伸缩。
- **判定偏移校准**：默认不动。结果页会报出本局的平均偏差，要用再点一下套用；也可以在设置里
  打开「每局自动套用」。
- 触摸派生的鼠标事件在 700ms 内被忽略，避免同一下吃掉两个音符。
- canvas 位置每 250ms 重新量一次，地址栏收放或旋转后不会按到错位的轨。
- 游戏中给 `body` 加 `.playing` 锁住页面，避免视口变化让判定线跳动。
- **事件时间戳换算**：不同浏览器 / WebView 的 `event.timeStamp` 基准各不相同，还可能在运行中漂移。
  引擎不去猜基准，而是持续记录 `performance.now() - timeStamp` 的**最小值**作为两个时钟的真实偏移
  （最小值对应排队耗时≈0 的那次事件），用 `timeStamp + 偏移` 换算。这样基准是什么都无所谓，
  漂移也能自动跟上，同时保留事件之间的相对精度（主线程卡顿时尤其重要）。
  换算结果若突然离当下超过 1 秒，说明基准跳变，会重新锚定并记一次异常。
- **卡顿是断触的主因**。安卓在应用主线程卡住期间会**直接丢掉排队的触摸**，表现就是
  「一段完全点不上，而且诊断面板上的数字一个都不动」。为此做了三件事：
  - 排期音频（节拍器 + BGM）改走一条可整体切断的总线，不再用数组持有几百个
    `AudioBufferSourceNode` 引用等着一次性释放——那正好制造周期性 GC 卡顿。
  - 画面上的两个渐变（轨道按下高亮、判定线）缓存复用，原来每帧每轨都新建，
    7K 下每秒要产生约 480 个渐变对象。
  - **渲染分辨率上限**（默认 2 倍）：手机屏幕常到 3 倍像素密度，填满一帧很吃力，
    降到 2 倍像素数少 56%，几乎看不出差别。连续卡顿 3 次会自动再降一档。
  - 引擎自己统计长帧（>120ms），结果页和诊断面板都会报出次数与最长帧。
- **区分「卡顿」与「触摸被丢」**。两者症状一样但病因完全不同，引擎分开测：
  - `stalls`：`_frame` 之间的间隔 >120ms，说明主线程卡住。
  - `presentStalls`：rAF 回调相对本帧 vsync 时刻的滞后 >120ms，说明 JS 在正常跑
    但帧没能按时上屏，属于显示/合成层问题。
  - `inputGaps`：连续敲击中间出现 >700ms 完全收不到输入的空档。
    **卡顿为 0 却有输入空档，就说明触摸是在页面之外被丢掉的。**
- **原始事件计数**（window 捕获阶段，早于一切处理与过滤）。用户反馈体感卡三秒时
  「连续掉帧」只有 0.1 秒，说明渲染循环根本没掉帧，那问题只可能是事件没送进来。
  这一层直接数 `touchstart/move/end/cancel/pointerdown`，并记录**原始事件空档**
  （>700ms 完全没有任何触摸事件）。它能把「浏览器没派发」和「派发了但被程序挡掉」
  彻底分开，也能看出是否出现 `touchcancel`（系统或浏览器中途接管手势）。
  模拟「浏览器停止派发」80 帧验证：报出 1367ms 空档且掉帧秒数为 0。
- **区分「一帧卡住」与「连着几十帧慢」**。用户报连续 3 秒卡死，但统计里单帧最大只有
  125ms——这两者原先的报表分不开。现在额外统计：连续低于 25fps 的最长时长与帧数，
  以及帧间隔直方图（顺畅 / 略慢 / 卡）。模拟连续 40 帧各卡 130ms 验证：
  报出「最长单帧 138ms、连续掉帧 5.27 秒 / 40 帧」，正是体感上的「卡死几秒」。
  渲染分辨率的自动降档也改成可逐级下降到 1.0，每档间隔至少 2 秒。
- **卡顿在光栅化，不在 JS**。用户设备实测归因是「我的代码 12ms / 代码之外 125ms」，
  且关掉全部声音照样卡——所以瓶颈既不是判定也不是音频，而是每帧填像素的开销
  （发生在合成线程，正好落在「代码之外」）。针对性减负：
  - 轨道按下高亮原本是每帧每轨一块 240px 高的**渐变填充**，四指狂按时四块常驻，
    渐变是逐像素运算。改成预渲染一张 1×64 的小图，每帧只做一次 `drawImage`。
  - 音符从圆角路径（4 段弧）改为直接 `fillRect`，这个尺寸下肉眼看不出差别。
  - 触屏设备的渲染分辨率上限默认降到 **1.5 倍**：3 倍密度下画布是 11.3MB，
    2 倍是 5MB，1.5 倍只有 2.9MB。
  - 新增**极简画面**开关：去掉拍线、按下高亮、打击特效，只留音符与判定线。
- **触摸事件按被动监听处理**：`touchmove` 在四指按住时每秒可达近千次，
  非被动监听会让浏览器每次都同步等 JS 返回并禁用事件合并。页面已有
  `touch-action: none`，不需要再 `preventDefault`。
- **输入路径零分配**：`_lanePos` 复用同一个对象返回，输入日志改用定长
  `Float64Array` 环形缓冲，不再每次击打都 push 一个新数组。
- **卡顿归因**：每帧分四段计时——音频排期 / 判定逻辑 / 绘制 / **我的代码之外**。
  最后一项 = 两帧起点间隔 减去 上一帧在本程序里花的时间，也就是浏览器自己干的活
  （GC、布局、合成、输入派发、跨线程同步）。结果页会直接说明卡顿该赖谁，
  不用再靠猜。注入 300ms 外部长任务验证：报出「我的代码 6ms、代码之外 304ms」。
- **降低音频线程负载**：去掉 `latencyHint: 'interactive'`（那会让音频线程以极短缓冲
  频繁唤醒，弱机上和主线程抢 CPU；判定用的是事件时间戳，本来就不依赖音频延迟）；
  软削波的 2 倍过采样改为不过采样；打击音限流为 20ms 内最多 4 个
  （和弦最多也就 4 押，不受影响，但挡得住四指连打把节点创建顶到失控）。
- **每次击打不再新建音频节点**（这是「越打越卡」的真正根因）。原先每响一次打击音就
  新建一个 `GainNode` 挂到总线上，而它永远不会断开——音频图随击打次数无限增长，
  每个渲染周期都要遍历，最后把线程拖死。这解释了为什么**交互（单键交替）几乎不卡、
  叠偶尔卡、四指狂按必卡且越来越卡**：卡顿程度和击打次数成正比。
  现在打击音走一条常驻的 `sfxBus`，BGM 每个乐器一条常驻增益节点，音符只连总线。
  实测 2000 次击打新建 GainNode 从 **2000 降到 0**，1000 个 BGM 音符从 **1000 降到 2**
  （两条乐器总线）。切片播放仍需独立包络，但播完会 `onended` 断开。
  四指狂按 15 秒 3600 次触摸：零卡顿、最长帧 17ms、全部记到。
- **视口变化不再重建画布**。地址栏伸缩、沉浸式状态栏进出、旋转都会连发十几次 `resize`，
  每次中间尺寸都重建一块 5MB（dpr 2）到 11MB（dpr 3）的画布后备缓冲，足以把主线程堵上
  几百毫秒——实测用户设备上出现过 325ms 的长帧，而安卓在主线程卡住期间会**直接丢掉排队的触摸**。
  现在播放中等尺寸稳定 220ms 后才处理，且只有变化超过 10% 才真正重建缓冲，
  小幅变化直接改变换矩阵拉伸复用。实测连发 21 次 resize 的重建次数从 21 降到 0。
- **解码后的 BGM 只留当前一条**。一条 12~16 秒立体声解码出来就是 4~5MB，
  五条都听过会留下 24MB，在手机上足以造成内存压力并引发大停顿。
- **低延迟画布默认关闭**。`desynchronized: true` 在部分安卓设备上会让画面周期性停更，
  而它只换来几毫秒延迟，得不偿失。设置里留了开关，改动后会重载页面。
- **不在打的时候自动退出全屏**：打完、暂停、返回设置都会退出，方便看结果和改设置。
- **断触自动检测**：输入日志记录最近 400 次击打（时刻、轨道、判定偏差、输入通道）。结果页会自动
  找出「有触摸但连续 1.2 秒以上一个都没打中」的区间并报出段数、总时长与触摸次数。
  诊断面板还会显示最近 3 秒的触摸/命中数与当前时钟偏移，断触发生的当下就能看见。
- 暂停与恢复倒数期间收到的输入单独计数，用来区分「没收到」和「收到但被丢弃」。
- 结果页显示「击打输入 / 命中 / 打空 / 边缘容错救回 / 暂停期丢弃」，命中数多于输入次数会直接报警。
  打空比例偏高时会提示多半是落点压在轨道边线上。
- 游戏设置里的**输入诊断**开关会在画面左上角实时显示这些计数、当前按住的手指数和上一次的判定偏差，
  可以边打边看是哪一环出问题。轨道被按下时判定线上会亮一条横杠，每一次被收到的输入都看得见。

静态服务 `serve.py` 发 `Cache-Control: no-cache`，资源带 `?v=` 版本号，避免 HTML 与 JS 版本错配。

## 文件

- `js/rng.js` 可复现随机数
- `js/generator.js` 谱面生成器（可在 Node 中 `require`）
- `js/audio.js` Web Audio 合成与录音播放
- `js/bgm.js` BGM 节奏型与和弦进行定义
- `js/game.js` Canvas 渲染与判定引擎
- `js/ui.js` 设置面板、预览、结果页
- `serve.py` 带 no-cache 头的静态服务（systemd `pekka-music.service` 用它）
- `deploy.sh` 同步到线上目录
